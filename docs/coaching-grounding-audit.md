## 0. 结论摘要

把系统拆成三层,三层的答案完全不同。**不是拍脑袋,但也从来没被验证过。**

| 层       | 问题                           | 结论                                                                                                                                                               |
| -------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **动词** | 「这件事发生过吗」             | **扎实。** 解析、DR 阶梯、可驱散类型、减伤百分比、冷却时长、天赋池,全部来自钉死版本号的官方 DB2,有再生成脚本。仅 `drCategoriesGenerated.ts` 就是 1,398 个官方 id。 |
| **名词** | 「哪个技能算 X」               | **薄。** 约 376 条手打条目分布在九张表里,**只有一张有漏项检测**,还是没人定期跑的手动 CLI。两张最大的自称是「等子项目 5 的管线」——管线从没建。                      |
| **副词** | 「这算不算错误、错到什么程度」 | **基本没有依据。** 决定「要不要指责玩家」的数字,绝大多数是当时觉得合适写下的,此后没动过。                                                                          |

**核心事实:没有任何机制验证过「这条判断是对的」。** 所有标定衡量的都是三类之一——发生率、模型行为(采纳率/审计通过率/filler 率)、确定性(跨后端一致度)。这不是本次审计的推断,是项目自己写下的:

> 「采纳率/审计通过率衡量的是『模型拿到一个候选之后处理得好不好』……但它们**不能证明『模型拿到的候选内容是对的』**」
> —— `$GLADLOG_EVAL_HOME/reports/raw-streams-ab.md:85`

> 「**测的是确定性,不是正确性。三家一致也可能三家都错;是否挑得对,只有第二步的人工盲评能回答**」
> —— `$GLADLOG_EVAL_HOME/selection-agreement-2026-08-13/REPORT.md:54` —— 它呼吁的那步人工盲评从未执行

判官的 `accuracy` 维度也不评正确性。rubric(`docs/commands/eval-baseline.md` Step 3)问的是 _"Does the response cite only events present in the prompt?"_,并明写 _"Generic advice is not a factual claim … **cannot** constitute an `accuracy` flaw"_——**教练建议本身被排除在评分之外**。

**结构性原因(这条最要紧):** 产品里对一条 finding 唯一的用户反馈是 `flag: "done" | "recurring" | null`(`packages/desktop/src/main/analysis.ts:1438`)——**没有「这条是错的」这个选项**。正确性数据在原理上就攒不起来。而胜负数据是存在的(`packages/analysis/src/learning/types.ts` 的 `LedgerRun.win`),**除测试 fixture 外没有任何代码读它**。

## B. 标定衡量了什么 —— 全量清单

| 指标                               | 怎么算                                    | 说明什么                                    |
| ---------------------------------- | ----------------------------------------- | ------------------------------------------- |
| 发生率 / 场均条数                  | 有候选的回合 ÷ 总回合                     | **频率**(且是全项目最有决策权的数字)        |
| 0.5–2 目标带                       | 场均条数的验收窗口                        | 频率                                        |
| 63.6% 历史上限                     | 既有类型的最高每场发生率                  | 频率 —— 而这个锚点本身有四重问题,见下       |
| 采纳率                             | 引用了新类型候选的 finding ÷ 全部 finding | 模型行为                                    |
| 审计通过率                         | `auditFindings` 五层通过率                | 事实忠实度 + 合规                           |
| filler 率                          | `severity="low"` 的占比                   | **明确标注为代理指标**                      |
| 跨后端 Jaccard                     | 三个后端选择的重合度                      | **确定性,报告自陈不是正确性**               |
| 判官 accuracy                      | 由 factAudit 计数确定性推出               | **文本对 prompt 的忠实度,明确排除教练建议** |
| 六个 hardFailure + positioningScan | 渲染文本的内部一致性 / 几何复算           | **测量自洽性**,不是判断正确性               |

**「63.6%」这个锚点四重问题**(四个新类型的阈值都是对着它调的):(1) 它是 gladlog 自己的数字,不是 arenacoach 的(arenacoach 公布的 DEATH-001 是 39.3%);(2) 被误标为 arenacoach 的 COOLDOWN 类,实际是 DEATH 类;(3) 它是**每场**口径,四个新率是**每回合**口径(约 3.35 回合/场),报告里点出了这一点然后照样比较;(4) 它自己也从未被验证过正确性。

**唯一的真值回路**:深挖评审台(`docs/commands/deepdive-probe.md` + `packages/eval/src/explore/reviewTypes.ts`),由**真实打这场的人**盲标 `truth / awareness / actionable / adopt / impact`。它是有效的,但总产出为:

- 全仓库唯一一份机器可读标注:`$GLADLOG_EVAL_HOME/review-sessions/2026-08-12-60ab1e8f.answers.json`,**15 条,1 场对局**
- 后续约 60 条只以散文形式存在于 `ledger.md`
- 盲法自陈偏弱(「格式可辨 + 深挖摘要提前曝光」)
- 设计目的里那句「用人工判断校准机器判据」**从未执行**——`answers.json` 在全代码库唯一的消费者是开发 UI 的解盲表格
- 唯一导出的正确性数字:**规范层错误率 ~17%**(58 条断言中 10 条可疑、2 条方向性错误),而且测的是深挖 agent 输出,**不是产品管线**

## D. 已核实的具体缺陷

以下四条全部在本次审计中逐条复核过,可直接动手。

### D1. ~~消散(47585)在同一场里有两个量级~~ —— **已修复 2026-08-17,提交 `27866802`**

> 修复方式不是改一条记录,而是把整个「什么算免疫 / 打进去算不算浪费」交给用户逐条签字的裁定册 `data/mitigationVerdicts.ts`(32 条四类 + `KILL_LIVE_HP_PCT = 20`),并删掉 `offensiveWasteAnalysis` 的两张手打名单。前后数字:出面回合 31 (10.3%) → 68 (22.7%),条数 43 → 104,三个此前完全静默的真免疫(破咒祝福/暗影斗篷/保护祝福)开始出面;击杀成立门实测挡下 1007 个条件类窗口里的 68 个 (6.8%)。详见交接文档 [`HANDOFF-2026-08-17-grounding.md`](HANDOFF-2026-08-17-grounding.md)。原始问题记录保留在下面。

### D1. 分散(Dispersion 47585)在同一场里有两个量级

官方表 `packages/analysis/src/data/mitigationGenerated.json` 的条目是 `"47585": { "pct": 75, "schoolMask": 127 }`,`mitigationData.ts` 里**没有 override**。但 `packages/analysis/src/utils/offensiveWasteAnalysis.ts` 的 `IMMUNITY_AURAS` 把它列为免疫,并因此套用更严的 2 次施法浪费门槛。于是一条路径告诉教练「你把伤害砸进免疫了,全浪费」,另一条同时算出「减免 75%」。这是 `CLAUDE.md` 共享谓词规则的典型违反:同一个技能,两个量级。

更大的背景:**「什么算免疫」有四张表,8 个 id 里只有 3 个是四表一致的**(`IMMUNITY_AURAS` 4 条 / `deathOutcomeAnalysis.IMMUNITY_SPELLS` 5 条 / `MITIGATION_TABLE` pct:100 共 7 条 / `SPELL_CATEGORIES` immunities 6 条)。无跨表一致性测试,未登记进谓词索引。

### D2. 恢复德永远被告知「没有规避手段」

`packages/analysis/src/utils/healerExposureAnalysis.ts` 的 `HEALER_AVOIDANCE_SPELLS` 只覆盖 6 个专精(恢复萨/神牧/戒律/奶骑/织雾/生命绑定),七个奶专精里**唯独漏了恢复德**。类型是 `Partial<Record<...>>`,查不到走 `?? []`,于是渲染出一句肯定的事实:`no avoidance tools available`。**一个关于表覆盖率的事实,被说成了关于游戏的事实。**

这属于「名词层缺项制造指控」的一类。同类还有两条,同样无守卫:`PURGE_BLOCKLIST` 缺项 → 指责玩家没驱散不可驱散的东西;`killWindowTargetSelection` 的敌方防御清单缺项 → 该敌人评分更「软」→ 凭空产生「本来有更好的目标」。(其余手工表的缺项方向多数是**静默**,相对安全。)

### D3. 被量出是废话的类型仍在出面

`juked-kick` 在 2026-07-19 的盲评里拿到 **2.9/5**,是五个类型里唯一低于 3.5 的,四个 ≤2 分全是它,理由是「read the fake cast, don't kick blindly」属于不言自明的通用建议。它被从进攻深挖里摘掉了——而代码注释自己写着:

> _"…so deepening only bolts context onto it and yields no new insight. **It stays a first-range finding**, it just isn't deepened."_ —— `packages/analysis/src/analysis/deepDive.ts` 的 `offensivePackItems` 注释

也就是说:量出来是废话,从深挖摘掉,**明确保留在用户实际会读的第一轮 finding 里**,`buildFindingsPrompt.ts` 的图例照旧让模型「Coach kick patience」。

对照组:`cd-hoarded` 是唯一被真正的正确性探针打中过的类型。意图守护(`castFailedInWindow`,读原始日志的 `SPELL_CAST_FAILED`)是全项目第一个把候选的核心主张与游戏自身权威信号对质的机制,结果 **35.6% 是冤枉的**(968/2720,1028 场 / 3434 回合)——玩家确实按了。深挖发现其中一个系统性根因:**26/26(100%)** 的终极苦修「囤积」声称 `readyT=0`,而日志证明不是(BACKLOG #29,跨回合冷却结转)。**当前处置是降一档严重度,是遮盖不是修复**——BACKLOG 自陈 `facts.t`/`facts.lateS` 底下仍然是错的。该类型 flag 为 `true`,问题开放未修。

### D4. 一处注释谎报自己的出处

## F. 缺口怎么补(选项,未拍板)

按「能不能真的产出正确性证据」排序,不按工作量:

1. **给 finding 加一个「这条是错的」反馈。** 现在只有 `done`/`recurring`。这是唯一能让正确性数据**自动累积**的改动,而且它把成本摊到日常使用里,不需要专门开评审场次。没有它,后面几条都是一次性的。
2. **把深挖评审台的 15 条扩成真的金标集。** 机制已经建好且有效,缺的只是量和执行。设计文档里那句「用人工判断校准机器判据」需要真的跑一次——否则现在这 15 条只是躺着。
3. **把判别力测量固化成一个可重复的脚本。** §C 是一次性的。作为常规体检它很便宜,而且能立刻标出「触发率 >50% 且判别力 <3pp」这类候选。**注意它只能证伪不能证实**——不该单独用它来砍掉一个类型。
4. **优先接地「制造指控」的三条路径**(§D2 列出的),因为它们的失效方向是凭空产生指责,而不是静默。
5. **给触发率 >50% 的类型定一条规矩。** 现有验收带上限是 70%,`cc-locked` 87% 是历史遗留没被这条带管过。到底多高算「在描述正常打法」,需要一个明确判据而不是逐个讨论。
